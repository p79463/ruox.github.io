    OLLVM 混淆 Pass 移植 LLVM 19 踩坑记

    2026-06-05 | 编译器

    背景

    OLLVM（Obfuscator-LLVM）是一个基于 LLVM 的代码混淆工具，通过 LLVM Pass 在编译阶段对程序进行混淆变换。 原始版本基于 LLVM 4.0，后续社区维护了 LLVM 14 版本。本项目的目标是将 OLLVM 移植到 LLVM 19。

    移植路线

    从 LLVM 14 → 17 → 19 逐步迁移。选择这条路线是因为 LLVM 的 API 在各个大版本之间变化较大， 跨度过大的直接迁移会导致大量编译错误难以排查。通过逐版本升级，可以更清晰地定位每个 API 变更点。

    主要挑战

    1. Pass Manager 重构 (LegacyPM → NewPM)

    LLVM 17 之后，Legacy Pass Manager 被彻底移除。OLLVM 的 Pass 继承自 llvm::FunctionPass， 需要改为继承 llvm::PassInfoMixin 并实现 run 方法。

    // LegacyPM (LLVM 14) struct HelloWorld : public FunctionPass {
      bool runOnFunction(Function &F) override {
        // ...
        return false;
      }
    };

    // NewPM (LLVM 19) struct HelloWorld : PassInfoMixin<HelloWorld> {
      PreservedAnalyses run(Function &F, FunctionAnalysisManager &AM) {
        // ...
        return PreservedAnalyses::none();
      }
    };

    这个变化影响深远：runOnFunction 的返回值从 bool 变为 PreservedAnalyses， Pass 注册方式从 INITIALIZE_PASS 宏变为 llvm::PassPluginLibraryInfo 或 ToolRun 模式。

    2. API 变更

    • CreateMessage 被替换 — LLVM 移除了旧的 CreateMessage API，需要改用新的 IRBuilder 接口或直接构造指令。
    • 模块 Pass 注册机制变更 — 从 PassManagerBuilder 回调方式变为 PassBuilder::addPass 链式注册。
    • AnalysisManager 的获取方式变化 — 不再通过 getAnalysis<T>() 获取分析结果，而是从 FunctionAnalysisManager 参数中通过 getResult<T>(F) 获取。
    • LLVMContext 和 Module 的接口变化 — 部分 LLVM IR 类的 getter/setter 被 const 化或改名。
    迁移过程中最大的陷阱是 Pass Registration。LLVM 19 要求显式声明 Pass 的依赖分析和 preserve 集合， 否则 Pass 链可能被优化器跳过或导致运行时断言失败。

    3. 控制流扁平化的实现

    基本原理：识别原始函数的控制流图，将所有基本块放入一个 switch-case 结构，通过 dispatcher 变量控制执行顺序。

    // 混淆前
    int foo(int x) {
      if (x > 0) return x + 1;
      else return x - 1;
    }

    // 混淆后（扁平化）
    int foo(int x) {
      int state = 0;
      while (1) {
        switch (state) {
          case 0: if (x > 0) state = 1; else state = 2; break;
          case 1: return x + 1;
          case 2: return x - 1;
        }
      }
    }

    在 LLVM IR 层面，这个变换需要：创建 switch 指令、将原基本块分裂成 case 块、插入 dispatcher 变量并确保 PHI 节点正确处理。 LLVM 19 中 SwitchInst 的 API 与旧版本兼容，但 SplitBlockAndInsertIfThen 等辅助函数的签名略有变化。

    4. 虚假控制流 Pass

    在原始基本块之间插入不可达的基本块，增加反编译器的分析难度。核心思路是在每个原始基本块前插入一个 opaque predicate， 使得静态分析工具无法确定哪些基本块是可达的。

    实现时需要在基本块之间插入一条永真条件的分支，然后添加一个永远不会被执行到的虚假分支。 为了避免优化器删除这些不可达代码，需要确保虚假分支中的指令对编译器来说是"不可证明"的。 常用的技巧包括：基于指针运算的复杂表达式、基于浮点运算的比较、或者通过内联汇编引入 barrier。

    测试与验证

    使用 test_ollvm 脚本验证编译产物是否包含混淆特征。验证方法包括：

    • 静态分析 — 使用 objdump / IDA Pro 检查编译产物的控制流图复杂度。
    • 符号特征检测 — 检查二进制中是否包含 LLVM 混淆 Pass 的特征字符串（可选的调试信息）。
    • 运行时行为对比 — 混淆前后的程序对相同输入应产生完全相同的输出。
    • 反编译器退化测试 — 使用 Ghidra / IDA 反编译混淆后的二进制，评估反编译结果的可读性。

    总结

    LLVM 新版本的 API 变化很大，但配合官方文档和社区经验可以完成迁移。 从 LLVM 14 到 19 的跨越需要重点关注 Pass Manager 重构、AnalysisManager 的使用方式、 以及 IRBuilder 和 指令构造 API 的变更。

    掌握 LLVM Pass 开发对于代码安全领域非常有价值。 混淆技术本身是一把双刃剑——既能保护知识产权和核心算法，也可能被用于恶意代码混淆。 理解其原理有助于在攻防两端都做出更明智的技术决策。
