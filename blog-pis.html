    地铁 PIS 系统通信协议设计
    CAN / RS232 / RS485 多协议架构

    项目背景

    乘客信息系统（Passenger Information System，简称 PIS）是城市轨道交通运营中至关重要的子系统之一。它承担着向乘客实时传递列车到站信息、换乘指引、紧急广播、运营公告等核心功能。一套稳定、可靠、实时的 PIS 通信架构，直接决定了乘客的出行体验和运营安全。

    在过去数年间，我有幸参与了国内多条地铁线路以及海外轨道交通项目的 PIS 系统设计与交付工作。这些项目覆盖了从站台 PIS 到车载 PIS 的完整场景，涉及 LCD 动态地图屏、LED 信息显示屏、车厢广播系统、座位状态显示屏等多种终端设备。面对不同线路对成本、可靠性、实时性和可维护性的差异化需求，我们逐渐沉淀出一套以 CAN 总线、RS232、RS485 三种物理层协议为核心的混合通信架构方案。本文将系统性地回顾这套多协议架构的设计思路、关键技术决策以及工程实践中遇到的典型问题。

    之所以没有选择工业以太网或无线通信作为统一方案，主要考量有三：一是轨道交通车载环境的电磁干扰极为严重，以太网 PHY 在强干扰下的稳定性不如差分总线；二是部分既有线路的利旧改造需要兼容几十米长的老式 RS485 线束，全面更换线缆成本过高；三是 CAN 总线在广播指令的实时性上具有天然优势，特别是紧急广播场景下，毫秒级的延迟差异可能影响安全。这些现实约束共同促成了多协议并存的技术路线。

    三种通信协议的选型

    CAN 总线：高可靠性的核心骨干

    CAN（Controller Area Network）总线是 PIS 系统中当之无愧的核心骨干。其 多主架构使得任意节点都可以在总线空闲时主动发起通信，无需主从轮询，这为紧急广播指令的实时下发提供了基础保障。CAN 总线的 载波监听多路访问/冲突检测（CSMA/CA + 位仲裁）机制能够在不损失数据的前提下自动解决总线冲突，优先级高的报文（如紧急广播帧）通过标识符仲裁必然获胜，这种硬件级别的实时性是以太网或 RS485 难以比拟的。

    在 PIS 系统中，CAN 总线主要承担以下关键数据交换：车厢主控制器与各 LCD 屏之间的状态同步和画面切换指令、广播主机向各音频播放器下发的紧急广播触发帧、以及座席屏的实时占用状态上报。每个 CAN 帧仅有 8 字节数据负载，但配合多帧扩展协议，完全可以覆盖上述场景。实际项目中，我们使用 500 kbps 的波特率，兼顾了传输距离（约 40 米的车厢级网络）和吞吐量。

    RS232：点对点的配置通道

    RS232 虽然在现代工业通信中逐渐被边缘化，但在 PIS 系统中它仍扮演着不可替代的角色——控制盒与广播主机之间的配置指令通道。RS232 是全双工的点对点通信，接口逻辑简单、驱动开发成本极低，非常适合用于设备调试、参数配置、固件升级等需要双向可靠交互的场景。

    实际布线中，控制盒通常位于司机室的操控台上，与广播主机之间的距离不超过 3 米，完全在 RS232 的标准通信距离（约 15 米）之内。我们采用 115200 bps 的波特率，数据格式为 8N1（8 位数据、无校验、1 位停止位）。控制盒通过 RS232 发送配置指令（如音量调节、广播模式切换、预录音频选择），广播主机收到后解析并执行，同时回传确认帧。由于该链路仅在系统初始化和运维阶段才高频使用，RS232 的低速率并不构成瓶颈，而其极低的硬件成本和对 MCU 内建 UART 外设的天然支持，使得它比 RS485 或 CAN 更适合这一角色。

    RS485：长距离的车厢级总线

    RS485 采用差分信号传输，具有极强的共模干扰抑制能力，通信距离理论可达 1200 米以上，且支持 最多 256 个节点 的多点组网。在 PIS 系统中，当需要跨车厢传输数据时（一列地铁通常有 6~8 节车厢），RS485 是性价比最高的选择。

    我们使用 RS485 构建了一条横贯全列的 车厢间数据总线，用于传输整车级的运营信息：当前站序、终点站、列车运行方向、下一站预告等。各车厢的主控制器通过 RS485 以 半双工主从轮询 的方式与列车级控制器通信。波特率设置为 250 kbps，在这个速率下信号在贯穿全列车约 200 米的线缆上仍然保持完整的眼图张开度。每个数据包长度控制在 128 字节以内，配合 CRC16 校验，确保跨车厢传输的可靠性。

    特性 CAN 总线 RS232 RS485
    通信方式 多主仲裁，广播式 点对点，全双工 多点，半双工
    最大节点数 理论 2³¹，实际 ≤ 110 2 ≤ 256
    典型距离 40 m @ 500 kbps 15 m @ 115200 bps 1200 m @ 250 kbps
    实时性 极高（硬件仲裁） 中（软件流控） 中（主从轮询）
    PIS 中用途 车厢内部核心数据交换 控制盒 ↔ 广播主机 车厢间数据传输
    硬件成本 中（需 CAN 控制器） 低（内建 UART） 低（内建 UART + 收发器）

    统一数据帧格式

    三种物理层协议各自有着不同的帧结构——CAN 有标准帧/扩展帧的 ID + 8 字节数据，RS232 和 RS485 则是纯粹的字节流。为了让上层应用程序不感知底层差异，我们设计了一套 统一的应用层数据帧格式，三种物理层之上都封装为同样的协议单元。

    /* 统一应用层数据帧格式 */
    // 帧头 (2B) + 长度 (1B) + 命令字 (1B) + 数据 (N) + 校验 (2B) + 帧尾 (2B)

    typedef struct __attribute__((packed)) {
        uint8_t head[2];     // 固定 0xAA 0x55
        uint8_t len;         // 数据域长度 (0-248)
        uint8_t cmd;         // 命令字
        uint8_t data[248];   // 数据负载
        uint16_t crc;        // CRC16-CCITT
        uint8_t tail[2];     // 固定 0x0D 0x0A
    } pis_frame_t;

    帧头 0xAA 0x55 用于接收方的字节对齐和帧同步检测。在 CAN 总线上，由于 CAN 控制器已经提供了硬件级的帧校验，因此应用层校验可以裁剪为简单的累加和；而在 RS232 和 RS485 字节流上，我们使用完整的 CRC16-CCITT 多项式校验，配合帧尾 0x0D 0x0A（CR+LF）确保帧边界的可靠识别。

    命令字（cmd）字段是整个协议的核心，它定义了 PIS 系统中所有设备交互的操作类型。我们将其划分为几个功能域：0x10~0x1F 为广播控制指令（紧急广播、预录广播、人工广播切换），0x20~0x2F 为显示控制指令（画面切换、亮度调节、字体缩放），0x30~0x3F 为状态查询指令（设备健康状态、固件版本、通信质量），0x40~0x4F 为固件升级指令（升级包传输、校验、重启）。这套命令字的域划分在后续多个项目中都保持了向后兼容。

    数据域的长度上限设为 248 字节，这是基于实际 PIS 应用场景的经验值：LCD 屏的画面切换指令通常只需要 20~50 字节的元数据；而固件升级分包传输时，每个分包的典型大小为 128~256 字节。248 字节既能够覆盖最大单帧传输需求，又不会在 RS485 半双工模式下因为一次发送过长而阻塞总线太久。在 CAN 总线上传输时，大于 8 字节的数据由底层适配层自动完成拆包和重组（使用 CAN 多帧传输协议，类似 ISO-TP）。

    中断优先级设计

    在嵌入式实时系统中，中断优先级的分配是一项决定系统实时性和可靠性的关键设计决策。PIS 系统中同时存在 CAN、UART（用于 RS232/RS485）、定时器、GPIO 等多种中断源，如果优先级分配不当，轻则导致广播指令丢包，重则引发系统级的音频卡顿或显示不同步。

    我们的优先级分配策略遵循一个核心原则：实时性要求最高的事件获得最高的中断优先级。在 PIS 系统中，广播指令的丢失会直接造成安全事故隐患（例如紧急疏散广播未能触发），因此 CAN 接收中断被设定为最高优先级。具体来说，在 STM32H743 平台上，我们将 CAN1 和 CAN2 的 RX0 中断设为抢占优先级 0、子优先级 0，确保任何时刻 CAN 报文到达时 CPU 都能立即响应。

    次高优先级分配给了 定时器中断（用于音频播放器的 DMA 双缓冲切换和 LCD 屏的刷新同步），抢占优先级 1。音频播放要求连续的 PCM 数据流，如果 DMA 缓冲区切换不及时会导致可闻的爆音或断续；LCD 屏的刷新需要精确的行场同步时序。这两者对实时性都有严格但可容忍微秒级抖动的需求。

    RS232 和 RS485 的 UART 接收中断被分配为 抢占优先级 2。字节流通信天然可以借助硬件 FIFO 或 DMA 来缓解中断频率。我们启用了 UART 的 FIFO 模式和空闲中断触发，这样 CPU 每收到一帧完整的报文才进入一次中断处理，而不是每字节中断一次，极大地降低了中断开销。在实际测试中，即使 RS485 总线上同时有 8 节车厢的数据突发（约 4 kbytes/s），CPU 的中断处理负载也低于 3%。

    此外，我们还设计了一套 中断安全的消息队列机制：所有中断服务程序只负责将接收到的原始帧写入一个无锁环形缓冲区（ring buffer），不进行任何协议解析操作。协议解析和命令分发由优先级最低的后台任务循环处理。这样做的好处是 ISR 的执行时间被严格控制在微秒级别，避免了因解析耗时导致的中断嵌套延迟。

    多设备协同

    一列地铁的一节车厢内通常部署了 4 类显示/音频终端：LCD 动态地图屏（2~4 块）、LED 信息屏（2 块，位于车门上方）、音频播放器（1 台，驱动 4~8 个扬声器）、座位状态显示屏（每排座位上方 1 块）。这些设备需要在毫秒级的时间尺度上协同工作，给乘客呈现一致的信息。

    协同机制以 车厢主控制器 为中枢，采用"发布-订阅"的消息模型。主控制器通过 CAN 总线周期性地广播"同步心跳帧"（每 100 ms 一次），心跳帧中携带了全局时间戳、当前运营状态（到站中/停站/离站/紧急）、以及最新的显示数据版本号。各终端设备收到心跳后，与本地状态进行比较，如果发现版本号不一致，则主动向主控制器请求最新的显示数据。

    具体到广播场景，当司机按下"紧急疏散广播"按钮时，控制盒通过 RS232 将指令发送给广播主机。广播主机收到指令后，立即执行以下操作：① 通过 CAN 总线广播"紧急广播触发帧"（最高优先级报文），命令所有音频播放器静音当前音轨并切换到紧急广播音频源，同时命令所有 LCD 屏切换到紧急显示页面；② 在 50 ms 内开始输出紧急广播音频；③ 持续广播紧急状态心跳帧，直到司机解除紧急状态。整个过程从按钮按下到 LCD 屏切换完成，实测延迟中位数为 23 ms，最差情况不超过 35 ms，完全满足地铁设计规范中"紧急广播反应时间 ≤ 200 ms"的要求。

    座位状态屏则是一个有趣的细节：每个座位下方安装有压力传感器或红外对射传感器，通过本地子控制器采集座位占用状态，然后通过 CAN 总线上报给主控制器。主控制器汇总全车厢的座位占用情况后，在 LCD 屏上显示为车厢俯视图，绿色表示空座、红色表示已占用。这一功能虽然看似简单，但涉及 28 个座位 × 6 节车厢 = 168 个传感器节点 的数据汇聚，对通信协议的效率和可靠性提出了不小的挑战。我们采用了"变化上报 + 定期轮询兜底"的策略：传感器子控制器仅在座位状态发生变化时才主动上报，同时每 10 秒强制上报一次当前状态作为心跳。这样既避免了频繁的 CAN 总线占用，又保证了数据不会因为丢帧而长期错乱。

    总结

    通过在多条地铁线路 PIS 项目中的反复迭代，我们这套以 CAN 总线为核心骨干、RS232 为本地配置通道、RS485 为车厢间传输链路的 多协议混合架构 已经得到了充分的工程验证。它的核心价值在于：不追求单一协议的万能性，而是在正确的位置使用正确的协议。

    回顾整个设计过程，有几个关键决策点值得记录：第一，统一应用层帧格式 使得上层业务逻辑完全与物理层解耦，后续更换或增加新的物理层（如改用以太网 CAN FD）时，仅需修改底层的适配代码；第二，中断优先级设计 遵循"ISR 最快处理、复杂逻辑丢给后台"的原则，确保系统的实时底线在任何负载下都不被突破；第三，发布-订阅式的设备协同模型 为系统增加了灵活性和可扩展性，新增一种终端设备只需要注册到心跳帧的订阅列表中，无需修改现有的通信流程。

    当然，这套方案也存在可以改进的方向。例如，目前 RS485 车厢间总线仍然采用主从轮询模式，在列车编组变长（如 12 节编组）时轮询周期会线性增加。未来可以考虑将车厢间总线升级为 CAN FD（数据场可达 64 字节）或者引入 TSN 以太网 来替代 RS485，实现更低延迟、更高带宽的车厢间通信。另外，随着 AI 技术在轨道交通中的渗透，PIS 系统未来可能需要承载视频分析（如客流统计、异常行为检测）等大带宽数据流，届时现有的 CAN/RS485 链路将难以胜任，以太网升级势在必行。

    轨道交通通信系统没有银弹，每种协议都有自己的适用边界。理解这些边界、在边界内做到极致，并且在系统层面优雅地将多种协议编织在一起——这才是嵌入式通信工程师真正的价值所在。希望本文的实践经验能够为从事轨道交通或工业物联网通信设计的同行们提供一些参考。
